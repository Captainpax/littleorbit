# Privacy design

Little Orbit is designed around two people sharing deliberately. It does not sell personal data, display advertising, or use answers or relationship activity to train or personalize AI. The 1.3 AI pipeline creates the same calendar-based question pool for the service. It may learn from separately consented, sanitized question-quality feedback only after K-anonymity thresholds are met; it never receives quiz answers or account, couple, note, location, or relationship data.

This document describes the implemented and published 1.3 behavior. A production privacy notice and legal review remain operational requirements for future changed data use.

## Consent and control

Registration is for adults and uses 18+ self-attestation without identity documents. Android asks separately for notification, precise foreground location, and background location permission. Location permission alone does not enable collection: both partners must also enable sharing in Little Orbit. Both partners must opt into intimacy questions; either partner can disable them immediately.

Unpairing stops new sharing immediately and deletes both relationship names and avatars. Each person receives a private read-only archive, but names and avatars are not copied into it and never transfer to a future partner. Only the other active partner can set, reset, replace, or remove a person's relationship identity; a person cannot set their own. Names reject controls, line breaks, email addresses, phone numbers, and URLs, and an account value that resembles contact information falls back to `You` or `Your partner` on relationship surfaces. Migration `0016` clears the old account-owned profile photos once because their ownership meaning cannot be converted safely. Smooch history is included in the private archive and never transfers to a future partner. It remains until either original participant's account-deletion job erases the relationship's Smooch rows. Users can export the name and avatar currently assigned to them and delete their account from the Android app; deletion jobs and bounded backup expiry must be visible and documented before launch.

The phone crops a chosen image to a square before upload. The server decodes JPEG, PNG, or WebP input, applies orientation, removes source metadata, and creates bounded 512-pixel and 128-pixel WebP variants. Only the current couple can fetch them, and only the subject's partner can mutate them. The phone keeps encrypted thumbnails and sends authorized names and thumbnails through the private Wearable Data Layer. The Wear launcher stores them in app-private files. Home widgets, tiles, and complications remain text-only.

Passive phone-to-watch records use opaque local relationship and managed-watch generations rather than an account identifier or server couple identifier. Sign-out, invalid or revoked session, unpairing, account deletion, or a server `relationship_inactive` response advances the relationship generation. Choosing, switching, or removing a watch advances the target generation. Records carry both barriers plus the selected Data Layer node ID; a non-target node clears itself when it observes a newer target generation. The watch applies purge markers first, rejects delayed older records, and checks both authorities again before finishing an asynchronous image write. If the watch cannot receive a purge, it marks data stale after six hours and deletes display values, names, thumbnails, configuration, queued actions, and partial files after 24 hours. Every surface read enforces the deadline even if the best-effort expiry alarm was delayed.

For each active Wear relationship generation, the first valid managed record also persists the controller phone's Data Layer node ID. Only that controller may receive watch status or Smooch requests or acknowledge/reject queued operations. Messages from another connected phone are ignored without revealing whether relationship state exists. The controller binding is cleared with the relationship purge barrier, sign-out, unpairing, managed-data expiry, or a new authorized generation. The binding never leaves device-local storage.

Countdown calendar export launches the installed calendar provider with a prefilled title, time or all-day date, timezone, and notes only after the person taps the action. Little Orbit receives no Google account token and does not read the resulting calendar entry. It does not synchronize later edits in either direction. Reminder offsets are account-private on the server; Android schedules the corresponding local notifications only when system permission and the countdown channel permit them.

## Our Space and attachments

Notes open in Markdown preview, but raw HTML is rendered as text and remote images are converted to deliberate links so opening a note cannot silently contact a third-party image host. Only an authorized `attachment://` image from the current note may render inline, after exact size and SHA-256 verification. Sanitized GIF animation stays on device and exposes pause/play; reduced-motion mode starts it paused. The Android editor keeps an app-private encrypted draft with its stable create identity and base revision. It autosaves after 800 milliseconds idle and at least every five seconds during continuous typing. Its ordinary Android saved-state bundle contains only an opaque workspace key; title, body, server snapshot, revisions, selection, and preview mode remain in Keystore-encrypted app storage. After process restoration, the app checks the current authorized server version before resuming live edits. Acknowledgements patch only the changed range and preserve both selection endpoints. If a newer server revision meets offline work, synchronization stops until the person reviews and merges, forks an attachment-safe copy, or chooses the shared version.

The picker accepts JPEG, PNG, WebP, GIF, PDF, plain text, Markdown, MP3, M4A, Ogg, MP4, and WebM. A file is limited to 100 MiB and the current couple is limited to 2 GiB. Uploads use stable operation IDs and exact offsets, and unscanned bytes stay in a private staging volume. ClamAV must report the file clean, then a type-specific sanitizer removes image, PDF, audio, or video metadata before the API makes the sanitized bytes available. Transparent still and animated images are rebuilt without losing their alpha frames. Because sanitization can change file size, the worker rechecks both limits under the couple lock before availability. Scanner outages fail closed and leave the item pending; malformed, infected, oversized, quota-exceeding, or unsanitizable content is quarantined or rejected. The API and owner console never expose attachment content or filenames to administrators.

Previews download only after current authorization and verify the sanitized SHA-256 digest. Temporary previews use the app cache. **Keep offline** copies a selected sanitized file into note-scoped app-private storage until the person removes that copy, deletes the attachment, signs out, unpairs, changes accounts, clears app data, or uninstalls Little Orbit. A successful active-and-recoverable note-directory refresh removes copies for notes whose restore window has ended. Audio and video previews are handed to a compatible installed viewer with a temporary read-only grant. Deleting an attachment hides it immediately for both partners and removes staging, available, cached, and kept-offline copies as each component next handles it. A structured `relationship_inactive` response clears Android drafts, transient uploads, preview cache, and retained note media without treating an ordinary revision conflict as an unpair event. Note purge also removes its server files.

## Couple activity timeline

The Home right panel shows up to 30 days of recent note, attachment, countdown, quiz, and Smooch changes for the active couple. A row stores a fixed event kind, actor reference, time, navigation target, optional note/countdown title, and the approved Smooch emoji when relevant. It never stores note bodies, attachment names or bytes, quiz prompts or answers, location data, email addresses, or free-form Smooch text. Retry-safe dedupe keys prevent duplicate events, and each partner has a separate monotonic seen watermark. Opening the panel advances only that person's position. Unpairing deletes the active-couple timeline rather than copying it into archives, and the worker purges rows older than 30 days. The owner console has no timeline viewer.

## Administrative access

The public website has no administrator interface. Big Orbit is a separately signed Android app whose P-256 public key is explicitly enrolled after password, a one-use terminal-issued bootstrap PIN, and proof of the matching non-exportable private key. The server stores only a domain-separated PIN hash; the eight-digit value expires after ten minutes, is invalidated after five failures, and invalidates every older live setup capability when a new PIN is issued. The restricted setup token cannot read ordinary administrator data or run operations. It may re-prove the same device key and rotate replacement credentials inside its original ten-minute window when the final enrollment response was lost. A first owner enrolls TOTP from a protected QR flow; enrollment of later devices does not expose or replace existing MFA. Ordinary short sessions remain bound to one approved device. Big Orbit exposes account state, service health, security events, batch status, attachment scan/rejection counts, reports, K-anonymous global-question intelligence, AI provenance, theme/context/reserve health, and privacy-safe counts. It has no route or viewer for note text, attachment names or bytes, quiz answers, relationship history, precise locations, or couple exports. Configuration responses use fixed allowlists; secret values and secret-bearing connection strings never enter a response.

An optional review is shown to Big Orbit or supplied to local weekly learning only when the author checked the separate learning-consent control, the text passed bounded safety/personal-data screening, and the question-week group contains feedback from at least five distinct accounts. Neither surface receives the author, couple, quiz day, or answer. Administrators can disable a global question or inspect its aggregate quality; they cannot trace feedback back to a relationship.

Administrator MFA replacement requires current password and current authenticator or recovery proof. A newly encrypted secret remains pending for a bounded enrollment window while the old factor stays active. Confirmation stores only hashed recovery codes, revokes every earlier session, and returns the new recovery codes once.

Daily quiz notifications identify only the UTC date and the availability, partner-finished, or results-ready transition. Their payload contains no prompt or answer content. Android may deliver a notification 15 minutes or more after the change because WorkManager controls durable background timing. If either person disables intimacy questions, unrevealed intimacy prompts are replaced immediately, affected drafts are deleted, and both completion markers are reset so the replacement must be reviewed.

Partner notification choices are stored with the account. Android permission and each notification channel remain local to a random app-installation UUID; Little Orbit does not use a hardware advertising identifier. Smooch, document-creation or edit, countdown, and quiz events are created only after the relevant accepted transition, and every enabled installation acknowledges independently after Android posts the alert. Turning off a category deletes its waiting ephemeral alerts so they do not appear after it is re-enabled. Unpairing deletes the former couple's notification events and disables both accounts' installations immediately. Little Orbit sends notifications only through its self-hosted service: the authenticated foreground WebSocket carries `notification.available`, and background WorkManager jobs poll the authenticated HTTPS endpoint. No Firebase, hosted push broker, provider token, or provider notification metadata is used or stored. A note alert contains the partner display name, note ID, and current title, never the note body or attachment metadata. Countdown alerts may include the shared title and identifier but exclude notes and reminder choices. Quiz alerts include only the UTC date. The public lock-screen version is always generic. A 30-minute document/editor cooldown prevents repetitive edit alerts, and no alert is created while the partner already views that note.

Foreground note and notification sockets retain a keyed session digest rather than the bearer token. The service rechecks that digest, account state, relationship access, and notification-installation state after connection and at most 30 seconds apart while idle. Revocation or loss of access closes the socket. Legacy quiz rows in account exports and former-relationship archives remain absent until both original participants answered that question.

Login, recovery, reset, pair redemption, and administrator proof limits store only scope-separated keyed hashes of supplied IP addresses, normalized emails, reset tokens, or account IDs with a capped count and timestamps. Raw subjects are not stored in the throttle table. Inactive rows are deleted within 24 hours plus the worker interval; security events record the blocked action and outcome without the attempted credential or relationship content.

A sender may create at most five Smooches in a rolling hour. The phone and managed watch each bound their encrypted handoff queue to five deliberate sends for 15 minutes and never invent a send after that window. The watch stores one approved emoji, UUID operation ID, creation time, and opaque current relationship/target generations; it never stores the account token. The phone accepts ownership only from the selected node after revalidating the current relationship, target generation, preference, emoji, UUID, and age, then uses the ordinary authenticated phone outbox. Weekly history uses the couple's chosen IANA home timezone and Monday-to-Sunday boundaries. Event payloads are fetchable for 24 hours, server records are purged within seven days, and installations unseen for 90 days are removed. WorkManager controls background timing, so a stopped app or OEM battery policy can delay an alert by 15 minutes or longer.

## Location processing

While signed in with local permission and mutual server consent, Android runs a visible foreground location service requesting a high-accuracy fix about every two minutes. Sign-in and signed-in process startup re-arm a 15-minute WorkManager OEM/process-recovery fallback, and paired foreground screens reconcile current permission and both consent states. Collection can continue into the encrypted queue while offline or temporarily throttled. Fixes older than two minutes are rejected locally. Each encrypted queue row carries the exact relationship ID and local relationship generation plus a timestamp, coordinate, accuracy, and stable sample ID. An upgrade from the old unscoped queue deletes those pending rows instead of guessing which relationship owns coordinates. The server accepts storage only while both partners consent, locks and verifies that exact relationship, rejects out-of-policy values, and deduplicates uploads. It schedules raw rows to expire five minutes before `recorded_at + 24 hours`, rejects an offline sample that has already reached that margin, and independently purges any row at the absolute 24-hour boundary even if its declared expiry is wrong. Either partner's opt-out stops the service immediately, clears the local queue, deletes both partners' raw coordinates, and rejects later uploads until both enable sharing again.

The estimate evaluates the chronological union of both streams so an intervening observation cannot disappear when the phones report at different rates. Direct nearby intervals require evidence no more than five minutes apart. When the next strong nearby anchor arrives within 20 minutes, the server may replace an unverified gap with a coordinate-free estimated bridge only if no intervening observation reports apart or poor accuracy. Open gaps never enter the durable total. Minute buckets retain observed, bridge, unverified, apart, and poor-accuracy provenance for 30 days and are grouped by the couple home timezone, including 23- and 25-hour daylight-saving days. Freshness is the older of the two members' newest retained samples, so one phone uploading alone makes the result stale. The five-minute live projection remains display-only and monotonic. Same Wi-Fi can prompt a new local sample but is never proximity proof; no SSID, BSSID, IP address, or network fingerprint leaves the phone.

Collection-health sharing is disabled by default for every installation. When enabled, the phone may share its model, battery percentage and charging state, network transport category, permission state, battery restriction state, tracking-notification state, upload health, queue size, and last check-in. It never shares a network name or address. The API returns the snapshot only to the active partner, omits installation identifiers, retains only current snapshots for 24 hours, excludes them from backups, and deletes them on opt-out or unpair.

## AI boundary

Ollama has no published port. The worker reaches it through an internal AI network; the one-shot initializer is the only other caller. Ollama has a separate egress-only bridge so it can download pinned generation and embedding model manifests, while no gateway, web, API, or database service shares that bridge. Generation prompts contain a calendar date, public generation rules, a bounded active learning policy, public weekly/day theme, limited recent global question text, bounded excerpts from reviewed repository Markdown, and optional bounded text from exact code-owned public HTTPS sources. Markdown files are selected only by a code-reviewed manifest, chunked and hashed before pgvector retrieval, and cannot introduce a new privacy source. A separate fetcher has no application secrets, refuses redirects and private addresses, and cannot choose an arbitrary URL.

Saturday learning may receive K-anonymous rating counts, average stars, fixed-tag counts, concept/category labels, and separately consented sanitized review text. A durable cursor lets later edits participate once eligible without rereading attributable history into the model. Reviews and public excerpts are treated as untrusted product feedback or inspiration, never model instructions, and are not reproduced. The system evaluates policy output deterministically and retains rejected policy metadata without activation. It does not fine-tune model weights. Generation and learning prompts contain no profiles, answers, custom couple questions, notes, locations, relationship history, email addresses, account/couple identifiers, or quiz-day identities.

Saturday at 09:00 in the configured IANA timezone also plans the next weekly arc; Sunday at 09:00 generates it. At most two days may center an inclusive observance. Sunday uses pinned Nomic embeddings plus exact/trigram checks to reject global concepts repeated in the batch, planned week, or preceding 365 days. The reviewed offline reserve contains 1,825 general and 365 intimacy entries with stable hashes and one-use state. Reserve content passes the same safety, consent, composition, and duplicate gates and contains no user-derived data. Generated candidates and public theme labels remain site-wide and are stored for administrator quality review.

Sanitized public-context snapshots may be used for at most 30 days after retrieval. When no current or permitted snapshot exists, generation continues from reviewed Markdown and reserve content and emits a content-free owner alert. Context snapshots, knowledge chunks, reserve state, weekly themes, and run provenance contain no account or relationship identifiers.

Coordinated PostgreSQL dumps exclude raw coordinates, collection-health snapshots, attributable feedback, feedback-operation records, and anonymous raw reviews. Aggregate counts and learned policy may be backed up because they cannot be linked to an account or couple. Attachment bytes remain encrypted relationship content and follow the bounded backup policy.

The planned 2.0 cycle tracker is outside this policy. It requires a separate health-data privacy, encryption, consent, deletion, abuse-risk, and medical-boundary review before implementation. Cycle data remains outside AI by default.

## App update boundary

The first RC10 launch asks whether automatic update detection should be enabled. If enabled, WorkManager checks public metadata about every six hours; a required compatibility update is checked regardless of that optional preference. The check sends only normal request network metadata plus the installed app name and numeric version code. The public release response and phone/Wear APK endpoints require no account data and contain no relationship data. The gateway receives ordinary download metadata such as IP address, time, requested version, and byte range; bounded operational logs follow the same privacy rules as other public requests. The phone stores the opt-in, last-check instant, release ID, progress phase, byte counts, optional defer state, and sanitized failure code in private app storage. It shows an optional prompt at most once per cold process while keeping an App updates banner available. Metadata work never downloads an APK. Android's `DownloadManager` and `PackageInstaller` act only after the person chooses to update, and a running or paused download with no progress for five minutes becomes an explicit retryable stalled state.

The in-app Wear installer uses local DNS-SD discovery or addresses typed by the person. While manual fields are open, their values are authoritative and discovery cannot replace them. Merely opening Watch settings or the installer never downloads an APK; metadata checks are public and APK bytes begin only after an explicit install, update, or repair action. The wizard sends the short-lived pairing code only to the selected local watch endpoint, clears it from the field immediately, disables saved view state and autofill for that field, and redacts it from object diagnostics. The phone proves the encrypted identity with a harmless authenticated command, checks privacy-safe device properties, and transfers the already verified public Wear APK over wireless ADB. It keeps the reusable ADB private key encrypted by Android Keystore until private removal, **Forget watch authorization**, or app-data clearing. Private removal first sends a target-generation purge and clears watch-originated queue entries, then uninstalls Little Orbit, forgets the phone key, and guides watch-side wireless-debugging revocation. The temporary Wear APK is held in the phone's private cache. Endpoint state stays in memory for the active installer, and safe failure records contain only a stage code. The server never receives the watch address, ports, pairing code, device fingerprint, model, or security patch.

The side-by-side smoke installer is restricted to the debug-signed `com.littleorbit.mobile.smoke` package. Its generated Wear APK is bundled only into the smoke phone artifact and its metadata is derived from those exact embedded bytes. Production/debug artifacts contain neither the QA APK nor QA labels, endpoints, or signing metadata. Both sources expose a fixed package and signer to verification and Kadb; neither accepts an arbitrary target supplied by a person.
